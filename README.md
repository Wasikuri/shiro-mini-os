# Shiro Mini OS v1.0.1

簡易的な自作OSです。GRUBから起動し、C+アセンブリで書いた独自カーネルが動作します（Linuxではありません）。

v0.3 では「必須級」の土台を一通り実装しました：割り込み、ページング、プリエンプティブ・マルチタスク、ディスク＋ファイルシステム、DHCP、そしてリング3で動くユーザープログラム（ELFローダ＋システムコール）。TCP/IPスタックとHTTPブラウザは v0.2 から引き続き搭載しています。

v0.4 では本格GUIを追加しました：`gui` コマンドでグラフィック画面に切り替わり、PS/2マウスでドラッグできるウィンドウ（Info / Term）＋タスクバーを持つデスクトップが動きます。ESCでテキストモードのシェルに戻ります（下記「GUI」）。

v0.5 では解像度設定を追加しました：`res` コマンドで 320×200（モード13h）／640×480／800×600／1024×768（Bochs VBE、32bpp）を切り替えられ、設定はディスクに保存されて次回起動・次回 `gui` に反映されます（下記「GUI」）。

v0.5.1 は「実用化」アップデートです：GUIのモダンデザイン刷新（角丸ウィンドウ、柔らかいドロップシャドウ、スレート系グラデーション、ダークなタスクバー）、フルスクリーンテキストエディタ `edit`、CMOS RTCを読む `date` コマンドとGUI時計の実時刻化、`cp` / `mv`、シェルのTab補完（コマンド名＋ファイル名）、コマンド履歴のディスク永続化を追加しました。

v0.6 では **HTTPS（TLS）対応** を追加しました：`browse https://...` が使えるようになり、SNI送信と証明書検証（ホスト名照合つき）を常時行います。TLSエンジンには BearSSL 0.6（MITライセンス）を採用しました（TLS用途に限りOSS利用。下記「HTTPS / TLS」）。

v0.6.1 では **アプリのインストール機構** を追加しました：`install <url>` でネットワークからELFアプリをダウンロードしてSHFSに登録し、`apps` で一覧、`run <name>` で実行、`uninstall <name>` で削除できます（下記「アプリのインストール」）。サンプルアプリとして対話式の整数電卓 `calc` が付属します。

v0.7 では **グラフィカルブラウザを本実装** しました：`web <url>` でタブ式ブラウザが開きます（下記「グラフィカルブラウザ」）。デザインはモダンなFirefox（Proton）風 — ダークなタブストリップに浮いた角丸のアクティブタブ、丸い一体型アドレスバー、最小限のツールバーです。ページ内JavaScript（Duktape 2.7.0、MIT）も実行します（JS用途に限りOSS利用。DOMは小さなサブセットのみ）。HTTPSページもそのまま開けます。

v0.7.1 では **TLSトラストアンカーを実サイト向けに拡張** しました：同梱ルートを2つから **120** に増やし、Mozilla CAバンドル（2026-10-20 時点のデータ、118ルート。GTS Root R1/R3/R4 を含む）を取り込みました。これで Google をはじめ大半の実サイトの証明書が検証できるようになります（下記「HTTPS / TLS」）。

v0.8 は **描画パイプライン刷新＋ブラウザのウィンドウ化** です：（1）GUIの描画を、VBE仮想画面2ページ分の **ページ切り替え（フリップ）**、**ダーティ矩形** の部分更新、**60fpsフレームペーシング** で再構成し、カクつきの主因だった「毎フレーム全画面コピー×2」を廃止しました。フレーム統計は Info ウィンドウとシェルの `gfxstats` コマンドで確認できます（下記「GUI」）。（2）ブラウザがフルスクリーン専用アプリから **デスクトップのウィンドウ** になりました：Info／Term と並ぶ「Web」ウィンドウとして開き、最大化・リサイズ（再レイアウト付き）・ドラッグ移動ができ、デスクトップアイコンやタスクバーからも開けます（下記「グラフィカルブラウザ」）。

v0.9 は **Vista風デスクトップ＋UEFI/GOPブート** です：（1）デスクトップが画像壁紙（オーロラ）＋左端アイコン列＋右端サイドバー（アナログ時計・カレンダー・統計ガジェット）＋ガラス風タイトルバーになりました（下記「GUI」）。壁紙は stb_image（パブリックドメイン/MIT）でデコードする JPEG アセットで、解像度に合わせて拡大・中央クロップします。（2）解像度に **1280×720 / 1280×1024** を追加（フリップ用2ページでも VRAM 16MB に収まる範囲まで）。（3）**UEFI ブート対応**：Multiboot2 ヘッダを追加し、同じ ISO が OVMF/UEFI でも起動するようになりました。ただし GRUB の EFI 版はフレームバッファタグ（タグ8）を渡さないため、GOP バックエンド（実装済み）は現状有効にならず、UEFI 時も GUI は DISPI/VBE で描画します（下記「UEFI ブートと GOP の現状」）。

v1.0 は **ブラウザ完成度アップ** です：グラフィカルブラウザに **CSSサブセット**（`<style>`／`style=""`／`<link rel=stylesheet>`、カスケード付き）、**画像表示**（`<img>` を http/https で取得し stb_image でデコード、フロー内配置）、**フォーム**（text/password/checkbox/radio/select/textarea、GET/POST送信＝POSTは新規実装のネットワーク経路）、**Cookieジャー**（メモリ内、ホスト単位、GUI終了で消去）を実装しました。あわせて、失敗したページ遷移（証明書エラー・404・到達不能・リダイレクト過多・巨大ページ）では **ブラウザからシェルに落とされず**、従来ページとステータスバーのエラー表示が残ることを回帰チェックで保証しています。ページ上限は 64KB → **256KB**、行上限は 512 → **1024行** に拡大（上限を超えたページは先頭から表示し、その旨をステータスバーに表示）。記事・Wikipedia・ブログ等の「コンテンツ系ページ」が概ね読める状態を目指した節目です（JSアプリ系サイトは原理的に非対応。下記「グラフィカルブラウザ」の制限を参照）。

v1.0.1 は **VirtualBox 互換パッチ** です：VBE（DISPI）描画で走査線ピッチを横幅×4と決め打ちしていたため、ピッチをパディングする環境（VirtualBox）で画面が斜行していました。BIOS のモード情報ブロックから実ピッチを読むようにし、ページ反転のページサイズもピッチ基準にしました（詳細は下記「テスト」の前の VirtualBox 注記）。機能追加はありません。

## できること
- VGAテキストモード（80x25）表示、スクロール、カーソル
- 自前GDT/IDT、PIC再マップ、PITタイマ割り込み（100Hz）
  - CPU例外はハングせず、例外名・ベクタ・アドレスを表示
  - キーボードはIRQ1＋リングバッファ方式
- メモリ管理：自前ページディレクトリ（4MB PSEページで全4GBをアイデンティティマップ、ただし0〜8MBは4KBページテーブル）、物理フレームアロケータ、ヒープ（kmalloc/kfree）
- プリエンプティブ・マルチタスク（タイマ割り込みによるラウンドロビン）
  - 右上の隅に稼働カウンタを表示するデモ用バックグラウンドタスク常駐
- ATA PIOドライバ＋独自ファイルシステム「SHFS」（下記）
  - 初回起動時にマジックが無ければ自動フォーマット
- ネットワーク（Intel e1000、ポーリング方式）
  - Ethernet / ARP / IPv4 / ICMP / UDP / TCP（クライアント）/ DNS / HTTP / **HTTPS（TLS 1.2、BearSSL）**
  - 起動時に **DHCP** でアドレス取得（QEMU slirp は 10.0.2.15 を配布）。応答が無い場合は静的設定 10.0.2.15/24、GW 10.0.2.2、DNS 10.0.2.3 にフォールバック
  - 簡易テキストブラウザ（HTMLタグ除去、script/style除去、ページ送り表示）
- ユーザープログラム：ELF32実行ファイルをリング3で実行（下記）
- シェル：コマンド履歴（↑↓、SHFSの `history` ファイルに永続化され再起動後も残る）、左右カーソル移動・行編集（←→、Home/End、Delete）、Tab補完（コマンド名とファイル名、候補が複数なら共通接頭辞まで補完し一覧表示）
- テキストエディタ `edit`：フルスクリーン編集、矢印キー移動、Ctrl+S保存、最大16KB
- 実時刻：CMOS RTC（0x70/0x71、UIP待ち、BCD変換、12/24時間両対応）を読む `date` コマンド。QEMUのRTCはUTCなので表示もUTC。GUIのタスクバー時計もRTCの HH:MM:SS 表示（読めない場合は起動時間表示にフォールバック）
- GUI（v0.4〜）：VGAレジスタ直接操作でモード13hに切替、ダブルバッファ描画、PS/2マウス（IRQ12）、ドラッグ可能な2ウィンドウ＋タスクバー（下記）。v0.5.1でモダンデザインに刷新（角丸・影付きウィンドウ、グラデーション背景、フラットな配色）
- 解像度設定（v0.5）：Bochs VBE（DISPI）による 640×480／800×600／1024×768（32bpp、リニアフレームバッファ）対応。`res` コマンドで切替、SHFSの `settings` ファイルに永続化

## テキストエディタ `edit`（v0.5.1で追加）
```sh
edit note.txt     # 既存ファイルを開く（無ければ新規）
```
- 全画面で編集します。矢印キーでカーソル移動（Home/Endで行頭・行末）、Backspace/Delete、Enterで改行。
- **Ctrl+S** で SHFS に保存。**Ctrl+Q**（またはESC）で終了しますが、**未保存の変更は破棄されます**（ステータスバーにも明記）。
- 対象ファイルが 16KB を超える場合は、開かずにメッセージを表示します。編集中のバッファ上限も 16KB です。
- 終了すると、シェルの画面はエディタ起動前の状態にそのまま復元されます（右上の隅カウンタもエディタ表示中は描画を止めます）。

## whois コマンド（v0.3.1で追加）
RFC 3912 の素のTCP（43番ポート）で問い合わせます：

```sh
whois example.com                 # whois.iana.org に問い合わせ
whois example.com 10.0.2.2        # サーバを明示指定（IPでも名前でも可）
```

- クエリ1行を送り、サーバが接続を閉じるまで応答テキストを受信してページ送り表示します。
- **紹介（referral）の扱い**：応答に行頭が `refer:` の行（IANA形式）が含まれていたら、同じクエリで紹介先サーバへ **1回だけ** 追従します。明示指定したサーバへの問い合わせでも追従し、紹介先が問い合わせたサーバ自身でも1回だけ再問い合わせします（追従は最大1回なのでループにはなりません。通常のIANA応答は別サーバを紹介するので、実運用では自然な動きになります）。
- DNS失敗・接続失敗・無応答はそれぞれメッセージを表示します。
- 注意：whois は平文の43番ポートを使うため、43番の外向き通信が塞がれたネットワークでは接続できません（この開発サンドボックスが該当します。通常のNAT環境＝VirtualBox等では問題ありません）。

## アプリのインストール（v0.6.1で追加）
ネットワークからアプリ（ユーザープログラム）を取ってきて、ディスクに永続化して実行できます。

```sh
install http://10.0.2.2/calc        # 名前はURLのファイル名から自動決定
install https://example.com/fizz.elf fizz   # 名前を明示指定（httpsも可）
apps                                # インストール済み一覧（名前とサイズ）
run calc                            # インストールしたアプリを実行
uninstall calc                      # 削除
```

- **パッケージ形式**：そのままのELF32実行ファイル（静的リンク、配置は `src/user/user.ld` 互換）です。登録情報は別ファイルに持たず、SHFS上のファイル名を `app.<名前>` とする規約で管理します（レジストリ＝ディレクトリ自体）。そのため `ls` でも見え、再起動後もそのまま残ります。
- **ダウンロード方式**：本文は64KBのページ取得バッファを通さず、`net.c` のストリーミングダウンロード（`net_download()`）でチャンクごとにSHFSへ直接書き込みます（fs側は連続セクタを先行予約するストリーミング書き込みAPIを使用）。HTTPのリダイレクト追従、Content-Length / chunked / 接続クローズ区切りのいずれにも対応します。
- **サイズ上限**：1アプリ最大 **512 KB**。超過した場合は転送を中断し、途中までのファイルは残りません。
- **重複インストール**：すでに同名のアプリがある場合はエラーにして終了します（上書きはしません。再インストールは `uninstall` してから）。
- **途中クラッシュへの耐性**：ディレクトリエントリはダウンロード完了時に初めてディスクへ書き込まれるため、転送中に電源が落ちても中途半端なアプリが登録されることはありません。ダウンロードした内容がELF32でない場合も登録を中止します。
- **サンドボックス**：インストールしたアプリも他のユーザープログラムと同じリング3＋`int 0x80`（write / read char / exit）の範囲でしか動作しません。この段階ではシステムコールを追加していません。
- **サンプルアプリ `calc`**：対話式の整数電卓（`src/user/calc.c`）。式を1行入力すると `= 答え` を表示し、空行で終了します。文法は `expr := term {('+'|'-') term}`、`term := factor {('*'|'/') factor}`、`factor := 数値 | '(' expr ')' | '-' factor | '+' factor`（空白無視、割り算は0方向への切り捨て、ゼロ除算と文法エラーはメッセージを出して継続）。
- **`run hello` との関係**：`run <名前>` はインストール済みアプリを探します。`run hello` は従来どおりカーネル埋め込みサンプルを指す特別扱いを維持しています。

## HTTPS / TLS（v0.6で追加）
`browse https://<url>` でTLS接続します。URLのスキームで平文/TLSを切り替えます（`https://` のデフォルトポートは443、リダイレクトもスキームを保持）。

- **エンジン**：BearSSL 0.6（MIT、(c) Thomas Pornin）を `third_party/bearssl/` に取り込み、`src/tls.c` のグルーで自前TCPクライアントの上に載せています。バージョン・取得元・SHA-256・ビルド設定は `third_party/README.md` に記録。BearSSLは TLS 1.0〜1.2 対応のため、**実際にネゴシエーションされるのは TLS 1.2** です。
- **実測したネゴシエーション結果**（QEMUハーネス実行時）：
  - ローカルテストサーバ（RSA証明書）：`TLS 1.2, ECDHE-RSA-AES256-GCM-SHA384`
  - 実サイト `https://example.com`：`TLS 1.2, ECDHE-ECDSA-CHACHA20-POLY1305`、`HTTP 200` で "Example Domain" を表示
  - 接続ごとに `TLS: connected, TLS 1.2, <スイート名>` という行を表示します
- **検証**：SNIを送信し、証明書チェーン＋ホスト名（SAN）を常時検証します。検証時刻はCMOS RTCから与えます。無関係なCAの証明書は `TLS: certificate not trusted (unknown CA).` と表示して拒否します（ハーネスで負例テスト済み）。
- **トラストアンカー**：カーネルイメージに同梱するルートは **120** です。内訳は (1) Mozilla CAバンドル（`https://curl.se/ca/cacert.pem`、Mozilla のデータ 2026-10-20 時点）の全118ルート、(2) ハーネス用にローカル生成したテストCA、(3) **SSL.com TLS ECC Root CA 2022**（Mozillaバンドルには無いが `example.com` の実チェーンの終端なので保持）。PEMは `third_party/certs/` に1証明書1ファイルで置き、`python3 third_party/make_anchors.py`（引数なしで `certs/*.pem` を全て変換）で `src/tls_anchors.h` を再生成できます（追加・更新はデータ変更のみ）。出典・フィンガープリント・更新手順は `third_party/README.md` の "Trust anchors" を参照。なお Mozilla が root store から外した **GTS Root R2 は現在のバンドルに含まれません**（Google の現行チェーンは R1 終端で検証できることを実機確認済み）。
- **エントロピー（正直な評価）**：種は SHA-256 で混合して BearSSL の HMAC_DRBG に投入します。内訳は (a) CPUIDが広告すれば RDRAND、(b) PITティック間スピン数のジッタ、(c) RTC時刻、(d) MACアドレス・自IP、カーネル内アドレス。ただし **QEMU（qemu32）では RDRAND が無いため (b)〜(d) の弱い混合が主体** で、エミュレータ環境でのジッタはエントロピー量が限られます。実機（RDRANDあり）では状況が改善しますが、このOSの乱数を高セキュリティ用途に使うべきではありません。
- **制限**：TLS 1.3 非対応（BearSSL 0.6 の上限）。クライアント証明書なし、セッション再開（チケット/ID）なし、OCSP等なし。ページ取得は従来どおり最大64KB、単一接続のみ。
- **ビルド上の注意**：対象CPU（qemu32）には SSE2/AES-NI が無いため、BearSSL はポータブルC実装のみでコンパイルしています（`-DBR_SSE2=0 -DBR_AES_X86NI=0`）。有効化するとサーバが ChaCha20 を選んだ際に #UD で落ちます（実測で確認・修正済み）。

## グラフィカルブラウザ（v0.7で追加、v0.8でウィンドウ化）
自前ブラウザエンジンの名前は **Tabby**（トラ猫 × ブラウザのタブ）です。HTML解析・レイアウト・描画は完全自前実装で、Blink／Gecko／WebKit のいずれでもありません（JSエンジンの Duktape、TLS の BearSSL、画像デコードの stb_image のみ、許可を得て OSS を利用）。
シェルで `web <url>` と打つと、GUIデスクトップが開いて **「Web」ウィンドウ** にそのページが表示されます（v0.7 まではフルスクリーン専用でした）。デスクトップ左下の **Webアイコンのダブルクリック** やタスクバーの **Webボタン** からも開けます（その場合はスタートページ）。取得には `net.c` のスキーム対応ダウンロードを使うため、**https:// のページもそのまま開けます**（検証範囲は同梱トラストアンカー120件。上記「HTTPS / TLS」参照）。ページ取得中はGUI全体が少し止まります（取得の進捗表示はテキストコンソール側に出ますが、グラフィック表示中は見えません。成否はウィンドウ下端のステータスバーに出ます）。

- **ウィンドウとして**：OSのウィンドウ枠でドラッグ移動・クリックで前面化・[x]で閉じる（タブの状態は保持され、再表示で続きから使えます）。タイトルバー右の **□ボタンで最大化**（作業領域いっぱい＝従来のフルスクリーン表示）／復元、右下の **グリップをドラッグしてリサイズ** すると、ドラッグ終了時にページを新しい幅で再レイアウトします（各タブにHTML原文を保持）。ESCはGUI全体の終了キーに戻りました（アドレス編集中だけは編集キャンセルとしてブラウザが使います）。最後のタブを Ctrl+W やタブの × で閉じるとウィンドウごと閉じます。

- **デザイン（Firefox Proton風）**：上部にダークなタブストリップ。アクティブタブは明るい「浮いた」角丸タブとして下のツールバーと同色でつながります。ツールバーは 戻る／進む／再読み込み のフラットなアイコンボタン＋**丸い一体型アドレスバー（ピル型）1つ**だけの最小構成。アドレスバーはクリックまたは Ctrl+L で編集でき、フォーカス中は明るいティールのリングを表示します。下端にはホバー中リンクのURLや `console.log` 出力を出す細いステータスバーがあります。
- **タブ**：最大6つ。各タブがページ（レイアウト済み行データ）、戻る／進む履歴スタック、スクロール位置、タイトルを保持します。タブのクリックで切替、タブ上の × または Ctrl+W で閉じ、Ctrl+T またはストリップの「+」で新規タブ（スタートページ＋アドレスバーにフォーカス）。Ctrl+R で再読み込み、←／→ キーでも戻る／進む、PgUp/PgDn・スクロールバーのドラッグでスクロール。
- **HTMLサブセット**：h1〜h6、p、div、span、a[href]（折り返し内でもクリック可能）、ul/ol/li、br、hr、table系は行として流す、title（タブに表示）、b/strong/i/em、body[bgcolor]、主要な文字実体参照。ページは最大 **256KB**（超過分は切り捨てて先頭から表示し、ステータスバーに明示）、表示は最大 **1024行** まで。レイアウトは行ベースのフローモデル（ブロックは積み重ね、インラインは折り返し）で、1行にウィジェット（画像／フォーム部品）は1つまで、という簡略化があります。各タブの行データ（1024行×約440B）はヒープから遅延確保します（タブを開いた分だけ、最大で6タブ×約450KB）。静的領域に置くとカーネルの終端がユーザープログラムのリンクアドレス 0x400000 を超えて ELF ローダに拒否されるため、この配置が必須です。
- **CSSサブセット（v1.0）**：`<style>` ブロック、`style=""` 属性、`<link rel="stylesheet">`（ページ読み込み時に取得）に対応。セレクタは要素名／`.class`／`#id`／インラインで、継承（colorとフォント系）＜ UAデフォルト ＜ 要素ルール ＜ クラス ＜ id ＜ インラインの小さなカスケード（同順位は後勝ち）。コンビネータは末尾の複合セレクタに読み替え、擬似クラスは除去します。対応プロパティ：`color`、`background-color`（+ `background` の色値）、`font-size`（px/キーワード/em/% → ビットマップ倍率1〜3に量子化）、`font-weight`（bold）、`font-style`（italic＝シアー変形）、`text-align`（left/center/right）、`text-decoration`（underline）、`display`（block/inline/none）、`margin`/`padding`（上下・左右の簡易モデル）、`border`（実線1px相当、ブロック自身の行範囲のみ）、`width`（px/%、ブロックと画像）、`line-height`（近似）、`list-style-type: none`。太字はにじませ、斜体はシアーで近似します。
- **画像（v1.0）**：`<img src alt>` を http/https で取得（相対URL解決あり）し、stb_image でデコード（JPEG/PNG、GIFは先頭フレーム）してフロー内に配置します。幅は CSS width ＞ width属性 ＞ 自然寸法の順で決め、コンテンツ幅でキャップ。高さは height属性か縦横比から算出（最大900px）。ページ背景へのアルファ合成付き。制限：エンコード済み **1MB超** の画像は読み飛ばし、デコード後 **約220万画素超**（または一辺4096px超）は却下、1ページ **16枚** まで、タブ当たりのデコード済み合計は **6MB** で打ち切り。取得はページ読み込みと同時に同期的に行うため、画像が多いページでは表示まで少し待ちます（失敗時は alt テキストを表示）。
- **フォーム（v1.0）**：`<form action method>` 配下の text／password（マスク表示）／checkbox／radio（グループ排他）／select（クリックで選択肢を循環）／textarea（複数行）／hidden／submit／button に対応。クリックでフォーカスし、キーボード入力はフォーカス中の部品へ配送。Tabキーで部品間を移動。送信時は「成功したコントロール」だけを集めて `application/x-www-form-urlencoded` 化し、GET は action のクエリに付けて遷移、POST は新規実装の POST 経路でボディ送信（301/302/303 は GET で再発行、307/308 はボディ維持）。テキスト欄での Enter は、フォームに submit ボタンがあれば送信します（暗黙送信）。送信結果は通常のページ遷移として履歴に残ります。
- **Cookie（v1.0）**：メモリ内ジャー。`Set-Cookie` をホスト単位で保持（8ホスト×4ペアまで、属性は無視して先頭の name=value のみ）し、同一ホストへの後続リクエストに `Cookie` ヘッダで送ります。**GUIを終了すると消去** され、ディスクには書きません。
- **遷移の堅牢性（v1.0）**：証明書エラー・404・DNS失敗・接続不能・リダイレクト上限超過・巨大ページのいずれでも、ブラウザ／GUIが落ちてシェルに戻されることはありません（従来ページが残り、ステータスバーに失敗を表示。リダイレクトは3回まで追随し、アドレスバーには最終URLが反映されます）。これは回帰チェック（`web` グループ）で各ケースごとに検証しています。
- **JavaScript（ページ内実行）**：エンジンは **Duktape 2.7.0（MIT）** を `third_party/duktape-2.7.0/` に取り込み、必要なlibc/libm表面は自作シム（`src/js_shims.c`、`src/js_math.c`、`src/js_setjmp.s`、`src/shim/`）でまかなっています（詳細は `third_party/README.md`）。`<script>` はレイアウト後に文書順で実行され、例外を投げても捕捉して残りの描画・後続スクリプトを続けます。スクリプトにファイル・ネットワーク・OSのAPIは渡しません。
  - **DOMサブセット（これだけです）**：
    - `document.title`：読み書き（タブのタイトルが変わります）
    - `document.write(str)`：HTML断片を **本文の末尾に追加** します（本物と違い、パース地点には差し込まれません）
    - `document.getElementById(id)`：要素オブジェクト（無ければ `null`）。`el.textContent` の読み書きに対応。要素は「表示行」単位で追跡されるため、ブロック要素に付けた id が正確な対象です（インライン要素では行全体が対象になります）。空のブロック要素にも1行分のスロットが確保されるので、空要素への代入も効きます
    - `console.log(...)`：ステータスバーに表示
  - スクリプトは1ブロック4KBまで、1ページ8ブロックまで。
- **制限（正直なところ）**：**JSアプリ系サイト（React等のSPA）は原理的に表示できません**（イベントハンドラ・タイマ・動的DOM構築が無いため）。記事・Wikipedia・ブログ・検索結果のようなコンテンツ系ページが対象です。レイアウトは行ベースの簡易フローモデルで、float／flex／grid／絶対配置は無く、表組みは行として流れます。CSSは上記サブセットのみ（フォントサイズは倍率1〜3に量子化、太字・斜体は近似）。リンクは原則として常にリンク色で描かれ、visited 等の区別はありません。フォーム部品は1行に1つまで、入力欄のキャレットは常に行末、select は循環式です。ページ内JSは上記サブセットのみで、タイマやイベントハンドラは無く、無限ループするスクリプトはページごと固まります（なお Duktape の致命的エラーは longjmp で捕捉してブラウザを継続しますが、その際のJSヒープは解放されず残ります）。大きなファイルの転送は QEMU/slirp 環境で約4KB/秒と遅く、256KB級のページでは読み込みに1分前後かかることがあります（上限で早期打ち切りするため無限には待ちません）。リサイズ時の再レイアウトではフォーム入力値は文書順が一致すれば保持されますが、スクリプトによるDOM書き換えは原文からの再実行で再現される範囲のみ残ります。320×200ではブラウザウィンドウも小さく、実用は最大化前提です。

## GUI（v0.4で追加、v0.5で解像度対応）
シェルで `gui` と打つとグラフィックデスクトップが起動します。

- **画面モード**：起動時は従来どおりVGAテキストモード3のまま。`gui` の時点で解像度設定（下記）に応じたグラフィックモードに切り替えます。Multibootヘッダではグラフィックモードを要求しないので、テキストコンソールや既存機能には影響しません。
  - **320×200**：VGAレジスタ（MISC/シーケンサ/CRTC/GC/AC＋DACパレット）を直接書いてモード13h（256色）に切替（v0.4方式）。
  - **640×480／800×600／1024×768／1280×720／1280×1024**：標準VGAの **Bochs VBE拡張（DISPI）** を使用。I/Oポート 0x01CE（インデックス）/0x01CF（データ）経由で、DISABLE→XRES/YRES/BPP=32→ENABLE|LFB の順に設定します。BIOS呼び出しは不要で、プロテクトモードのまま切り替えられます。IDレジスタが 0xB0Cx 系でない環境（VBE非対応）では自動的にモード13hへフォールバックし、その旨をシェルに表示します。高解像度は v0.9 で追加：ページ切り替えには表示ページ＋裏ページの2面が必要で、1280×1024×32bpp×2面＝約10.5MB は QEMU 標準VGAの VRAM 16MB に収まりますが、1920×1080×2面＝約16.6MB は収まらないため提供しません。実際に使えるかどうかは推測せず、VBE情報ブロックの総メモリ量（DISPIの VIDEO_MEMORY_64K）と要求量を照合して決めます（2面取れない場合は1面＋部分転送に落とします）。
  - **リニアフレームバッファ（LFB）**：PCIコンフィギュレーション空間（0xCF8/0xCFC）を走査して VGAクラス（0x0300）のデバイスを探し、BAR0 から取得します（アドレスは固定しません）。カーネルは全4GBをアイデンティティマップしているため、LFBはそのまま読み書きできます。要求メモリ量がデバイスのビデオメモリ量（DISPIの VIDEO_MEMORY_64K レジスタ）を超えるモードは設定しません。
  - 終了時（ESC／Exit）は VBE を無効化してから、モード13h経路と同じ手順（フォント復元＋テキストモード3のレジスタテーブル）でテキスト画面に戻ります。
- **解像度設定（`res` コマンド、v0.5）**：
  ```sh
  res            # 現在の設定と選択肢を表示
  res 800 600    # 800×600 に設定（res 800x600 でも可）
  ```
  設定は SHFS の `settings` ファイル（`res=800x600` という1行）に保存され、起動時に読み込まれて次回の `gui` に使われます。未設定時のデフォルトは 320×200（モード13h）で、v0.4 と同じ動作です。Infoウィンドウにも現在の解像度が表示されます。
- **フォント保存/復元**：モード13hの描画はプレーン2のフォント領域を壊すため、切替前に8×16フォント（256文字分）をヒープに退避し、終了時に書き戻してからテキストモードのレジスタテーブルを適用します。これでESC終了後も文字化けしません。
- **描画（v0.8で刷新）**：描画プリミティブは実行時の画面幅・高さ・ピクセル形式（8bppパレット／32bpp XRGB）に対応しており、32bppではパレット色を同じ色表から XRGB に変換して描きます。文字は退避したVGAフォントのグリフをそのまま使います。パイプラインは次のとおりです。
  - **ページ切り替え（VBE時）**：仮想画面を縦2ページ分（VIRTUAL_HEIGHT = 2×表示高）確保し、RAMバックバッファで合成した変更分を裏ページへ転送してから、垂直帰線の検出（0x3DA bit3、短時間ポーリング）に合わせて Y_OFFSET を切り替えます。表示中ページに書き込まないので、途中のフレームが見えることはありません。全画面転送は最悪でも1フレームに1回までで、カーソルだけのフレームは差分転送のみです。仮想画面が取れない場合は1ページ＋部分転送、モード13hでは RAMバックバッファ＋帰線に合わせた転送にフォールバックします（旧来の「合成バッファ」は廃止）。
  - **ダーティ矩形**：ウィンドウの移動・フォーカス変更・時計の秒更新・Termのカーソル点滅（プロンプト行だけ）などで汚れた矩形だけを再合成・転送します。
  - **フレームペーシング**：100Hzタイマ上で 2,2,1 ティック間隔（平均16.7ms）のスロット制＝最大60fps。入力を集めてから1回だけ描くので、ドラッグ中もフレーム予算を超えません。
  - **実測（QEMU TCG、ゲスト内カウンタ `gfxstats`）**：ウィンドウを約3秒ドラッグし続けたときの平均は **800×600 で約54fps**（負荷により 37〜54 の範囲）、**1024×768 で約56fps**。同じドラッグでの合成＋転送能力そのものは上限を外すと約238fpsあり、頭打ちはペーサ（60fps）側です。最悪フレームはセッション開始直後の全画面フレーム等で 60〜100ms。数値はホスト負荷でぶれます（自動テストの合否バーは余裕を見て30fpsに設定）。
  - **フレーム統計**：Infoウィンドウに現在のFPSをライブ表示。シェルに戻ってから `gfxstats` で、直近セッションの解像度・方式（page-flip／dirty blit）・vsync検出・平均FPS・最悪フレーム時間・総転送量を確認できます。
- **デスクトップ（v0.9でVista風に刷新）**：Windows Vista のデスクトップをモチーフに再構成しました。
  - **壁紙**：オーロラ画像（`assets/wallpaper.jpg`、ホスト側スクリプト `tools/make_wallpaper.py` で合成したJPEGアセット）を **stb_image**（パブリックドメイン/MIT、third_party/README 参照）でデコードし、画面解像度に合わせてバイリニア拡大＋中央クロップ（cover-fit）して敷きます。デコード済み画像は最大640px幅に縮小してキャッシュし、現在のピクセル形式（32bppではXRGBワード、モード13hではパレット索引）に変換した画面サイズのバッファをモードごとに1回だけ生成します。デコードや確保に失敗した場合は従来のスレートブルーの縦グラデーション（48段のパレットランプ）にフォールバックします。
  - **アイコン列**：左端に Web／Term／Info のアイコン（描画グリフ＋英字ラベル＋影付き文字）を縦に並べます。シングルクリックで選択（半透明のハイライト）、ダブルクリックで起動。ラベルが英語なのは日本語フォントがまだ無いためです（VGAフォントの英数字のみ使用）。
  - **サイドバー**：幅800以上のとき右端に半透明パネルを表示（320×200では非表示）。**アナログ時計**（RTCの時分秒で針を描画、秒針は赤、デジタル読み出し併記）、**カレンダー**（RTCの年月、当月を表示し今日をアクセント色で強調）、**統計ガジェット**（稼働時間・現在のFPS・RAM容量）。毎秒、サイドバーの矩形だけをダーティ矩形として再描画するので時計は生きたまま低コストです。
  - **ガラス風タイトルバー**：32bppではタイトルバーを単色で塗らず、RAMバックバッファ上で **背景に対して半透明ブレンド** します（上部ほど不透明度が高く、上半分には白いスペキュラの光沢がフェードイン）。これは Vista Aero の見た目を狙った「ガラス風」であり、背景ぼかし（ブラー）は実装していません。8bpp（モード13h）では従来どおり単色です。
  - 下部タスクバーは従来どおり：ダークスレート地、アクセント色の「Shiro」ピル、角丸ボタン、右にRTC実時刻クロック HH:MM:SS。ウィンドウは角丸＋細い暗色ボーダー＋柔らかいドロップシャドウ（32bppでは減衰ブレンド）。
- **ウィンドウ**：
  - **Info**：バージョン、RAM容量、稼働時間、現在のFPSを表示。琥珀色の角丸アイコン付き。
  - **Term**：簡易コンソール（`help` / `clear` / `echo` / `about` / `uptime`）。フォーカス中はキー入力がこちらに入ります。
  - **Web**（v0.8）：グラフィカルブラウザ（下記）。最初は隠れていて、デスクトップアイコンのダブルクリック／タスクバーのWebボタン／シェルの `web` コマンドで開きます。□ボタンで最大化、右下グリップでリサイズ。
  - タイトルバーをドラッグして移動、クリックで前面化、[x]で閉じ、タスクバーのボタンで再表示。ExitボタンかESCでシェルに戻ります。
- **マウス**：PS/2マウスをIRQ12割り込みで処理（3バイトパケット組立、現在の解像度内にクランプ）。初期位置は画面中央。シェルの `mouse` コマンドで受信状態を確認できます。
  - 実装上の注意：モード切替直後に届くACKバイト（0xFA）がパケット開始位置をずらす問題があったため、パケット開始バイトの検証（overflowビット付きを棄却）と、開始時のフラッシュ（mouse_flush）で対策しています。
  - QEMUのモニタ `mouse_move` はこの構成では「相対移動」として働きます（引数がそのまま符号付きデルタになることをゲスト側 `mouse` コマンドで実測）。Webターミナルのマウス送信もこの前提でデルタ変換しています。

## UEFI ブート（v0.9で追加）と GOP の現状
ISO は **BIOS / UEFI ハイブリッド** です（grub-mkrescue が BIOS 用と EFI 用の両方の El Torito イメージを生成）。UEFI 環境（QEMU では OVMF）では GRUB の EFI アプリがカーネルを **Multiboot2** で起動し、シェル・ファイルシステム・ネットワーク・GUI デスクトップまで BIOS 時と同様に動作します（`tests/qemu_test.py uefi` で検証）。

- **Multiboot2 対応**：カーネルイメージには Multiboot1 と Multiboot2 の両方のヘッダが入っています（MB2 ではフレームバッファ 1024×768×32 を要求）。GRUB は BIOS／EFI どちらの起動でも `multiboot2` コマンドで読み込みます。カーネルはマジックで判別し、MB2 のメモリマップ（タグ6、なければタグ4）から RAM 容量を取得し、EFI システムテーブルタグ（11/12）の有無で UEFI 起動を判定します（MB1 経路は従来どおり）。
- **GOP フレームバッファタグは GRUB（EFI版）が渡しません**：Multiboot2 フレームバッファタグ（タイプ8）の解釈と GOP バックエンド（アドレス・**ピッチ**・幅・高さ・bpp・RGB フィールド位置をタグから組み立て、フリップなし・ダーティ矩形転送で描画）は実装済みですが、**GRUB の EFI 版 multiboot2 ローダはタグ8を生成しません**（起動中のゲストで解釈結果 `gop.valid == 0` を直接確認）。そのため現在の UEFI 起動ではブートログに正直に `Boot: UEFI (Multiboot2), no GOP framebuffer tag` と出し、GUI は標準 VGA の **DISPI/VBE バックエンド**で描画します（OVMF の QemuVideo 自体が DISPI デバイスなので、解像度変更もページ切り替えもそのまま効きます）。タグを渡すローダで起動した場合は GOP バックエンドが有効になり、その場合のみ解像度はファームウェア固定（`res` が変更を拒否）・フリップなしになります。本物の GOP を得るには、カーネル自体を EFI アプリケーションとして起動し ExitBootServices 前に GOP を読む専用スタブローダが必要で、将来課題です。
- **テキストシェル**：Multiboot2 起動では、GRUB／ファームウェアがグラフィックモードを設定した状態でカーネルへ入ります。そのためカーネルは MB2 起動の直後に **Bochs VBE（DISPI）を無効化** し（有効なままだと表示タイミングも 0xB8000 のアパーチャも VBE 側が握り、テキスト出力がリニアフレームバッファへ吸い込まれます）、内蔵フォント（SeaBIOS 由来の 8×16 グリフデータ `src/font8x16.h`）を VGA プレーン2へ書き込み、テキストモード3のレジスタテーブルを適用して **テキストモードを再構成** します。
- **ファームウェアの後始末（UEFI 起動に必要だった修正）**：UEFI ファームウェアはデバイスを BIOS と違う状態で残します。(1) IDE コントローラの PCI I/O デコードが無効のことがあり、そのままだと ATA ステータスが 0x00 を返し続け全コマンドがタイムアウトする → ATA 初期化で I/O デコードを有効化し、デバイスへソフトウェアリセット（SRST）を発行してから IDENTIFY する。(2) VGA も同様で、DISPI 探査の前に PCI の I/O＋メモリデコードを有効化する。(3) GUI のグリフはプレーン2からのキャプチャではなく内蔵フォントから直接初期化する（ファームウェアフォントの存在に依存しない）。いずれも BIOS 起動では無害な冪等処理です。
- **既知の制限（UEFI時）**：OVMF ではテキストモードのグリフが実画面に描画されません（テキストメモリの内容自体は正しく、シェルの入出力・自動テストは正常。GUI デスクトップは無関係に完全動作）。プレーン2へのフォント書き込みがファームウェアの GOP 状態では保持されないためで、原因の特定までは至っていません。
- **バックエンドの確認方法**：シェルの `gfxstats` が実際に使った描画経路（`GOP (UEFI)` / `VBE`）を表示します。Info ウィンドウの Graphics 行も同様です。

## Webターミナル（webterm/）
`webterm/server.py`（127.0.0.1:8090）がQEMUゲストを内蔵し、ブラウザから操作できます。

- テキスト画面ビュー：VGAテキストメモリを読み取り、色付きで表示。キー入力は sendkey で注入。
- **画像ビュー（v0.4）**：QEMUモニタの `screendump` でフレームバッファをPPM取得し、純PythonでPNGに変換して表示（`GET /api/fb.png`、約1.2秒ごとに更新）。テキスト画面（720×400）でもGUI画面（640×400）でもそのまま映ります。v0.5の高解像度モードでは、その解像度（例：800×600）のまま表示されます。
- **マウス対応**：画像ビュー上でのポインタ操作（押下・ドラッグ・離す）を `POST /api/mouse` で受け、サーバ側で保持する推定カーソル位置とのデルタに変換してモニタ `mouse_move` / `mouse_button` を発行します。GUIのウィンドウをブラウザからドラッグできます。
- ページには `gui` 起動ボタンと ESC ボタンもあります。アクセスキー認証はテキスト画面と共通です（画像だけ `<img>` の制約上クエリパラメータでも受け付けます）。

## ファイルシステム（SHFS）のレイアウト
セクタ＝512バイト固定です。

| セクタ | 内容 |
|---|---|
| 0 | スーパーブロック：マジック `0x53484653` ("SHFS")、総セクタ数、各領域の位置 |
| 1〜8 | ディレクトリ：64エントリ×64バイト `{ name[28], used, start_sector, size_bytes, alloc_sectors, reserved[5] }` |
| 9〜12 | 割り当てビットマップ：1セクタ＝1ビット（最大16384セクタ＝8MBまで） |
| 16〜 | ファイルデータ：連続したセクタのランで割り当て |

ファイルは1つの連続ランに格納されます。`write` は既存ファイルを解放してから再割り当てします。メタデータ（ディレクトリ＋ビットマップ）は変更のたびに書き戻します（ライトスルー）。なお `fs_write_file()` はRAM上に全体を持つ都合で60KBまでに制限していますが、`install` が使うストリーミング書き込みAPI（予約→逐次書き込み→コミット時に初めてメタデータを同期）はこの制限を受けず、512KBまで扱えます。

## ユーザープログラムとシステムコール
- `run hello`：カーネルに埋め込まれたサンプル（`src/user/hello.c`）を実行。挨拶を表示し、打った3文字をエコーして終了コード3で終了します。
- ELFローダ：静的リンクされたELF32（ET_EXEC、x86）を 1MB〜8MB のユーザーウィンドウに配置し、フレームをユーザーページとしてマップ、ユーザースタック（最上位ページ）を用意してリング3へ遷移します。カーネルイメージと重なるセグメントは拒否します。ユーザーモードで例外が発生した場合はシェルに戻ります。
- システムコールは `int 0x80`：
  - `eax=1` write（ebx=バッファ, ecx=長さ）→ eax=書いた長さ
  - `eax=2` read char → eax=文字（ブロッキング）
  - `eax=3` exit（ebx=終了コード）
- サンプルのビルドは Makefile が行います：`src/user/hello.c` を `src/user/user.ld`（配置 0x400000）でリンクし、`ld -b binary` でカーネルに埋め込みます。
- **アプリ作成上の注意**：`int 0x80` のインライン asm には必ず `"memory"` クロバを付けてください。無いと、GCC が「カーネルだけが読むバッファ」へのストアを最適化で消してしまい、スタック上のバッファを渡す write が NUL を表示する、という事故が起きます（v0.6.1 で `hello` / `calc` のラッパに修正済み。カーネル側の問題ではありませんでした）。
- `exec <name>` 用のディスクイメージは `tests/build_fs_image.py` でホスト側から作成できます。

## ビルドと起動
```sh
make            # shiro-os.iso ができる
make run        # QEMUで起動（disk.img を自動作成、e1000 + ユーザーネット付き）
```
`make run` は `disk.img`（8MB、生イメージ）が無ければ作成し、IDEプライマリマスタとして接続します（ISOはCDから起動）。

手動で起動する場合：
```sh
qemu-system-i386 -cdrom shiro-os.iso -boot d -m 128 \
    -drive file=disk.img,format=raw,if=ide,index=0 \
    -device e1000,netdev=net0 -netdev user,id=net0
```

必要なもの: gcc, binutils, grub-mkrescue（Debian/Ubuntu では UEFI 用モジュールの grub-efi-amd64-bin も。これが無いと ISO が BIOS 専用になります）, xorriso, mtools（`assets/wallpaper.jpg` を含まないチェックアウトでは、壁紙を python3 + PIL で再生成します）

VirtualBox / VMware では、ISOをCDとしてマウントし、NICを Intel PRO/1000（e1000）系 + NAT、ディスクをIDEプライマリに接続すれば起動できます。

なお VirtualBox の標準VGAも Bochs VBE（DISPI）を公開しているため高解像度モードは動作する見込みですが、ファームウェアやバージョンによって挙動が異なる場合があります（その場合は 320×200 にフォールバックします）。

**VirtualBox での表示の斜行について（v1.0.1で修正）**：VirtualBox は VBE モードの走査線ピッチ（1行分のバイト数）を 横幅×4 バイトより大きく取る（パディングする）場合があり、ピッチ＝横幅×4 と決め打ちしていた v1.0 までは、デスクトップや壁紙が1行ごとに少しずつずれて斜めに崩れて見えました。v1.0.1 では、BIOS 起動時に VBE モード情報ブロック（int 10h AX=4F01）をリアルモード・トランポリンで取得し、`LinBytesPerScanLine`（無ければ `BytesPerScanLine`）を実際のピッチとして採用します（フリップ時のページサイズもピッチ×高さに変更）。採用したピッチは `gfxstats` の先頭行に `pitch <値> (bios)` と表示され、Info ウィンドウの Graphics 行にも（パディングされている場合のみ）出ます。QEMU ではピッチ＝横幅×4 が返るため、従来と完全に同じ動作です。なおグラフィックスコントローラは **VBoxVGA** を推奨します（VirtualBox のもう一方の選択肢 VMSVGA は VMware SVGA 互換で、本OSが使う Bochs DISPI の対象ではありません）。UEFI 起動時は BIOS 呼び出しが使えないためピッチ取得は行わず、GOP のピッチ（ファームウェア提供）または従来の決め打ちを使います。また、ウィンドウサイズに合わせた解像度の自動調整は、Guest Additions 相当のドライバが無いため行いません（`res` コマンドで固定解像度を選んでください）。

## テスト
`tests/qemu_test.py` がQEMU（TCG）で自動テストします：起動・uptime・mem、ps＋隅カウンタ、DHCP、シェル履歴・行編集・Tab補完、run hello、`date` のRTC時刻（ホストUTCとの近さも検証）、ネットワーク回帰（ping/dns/browse）、ファイルシステム（書き込み→再起動→読み出し永続性、cp/mv、`edit` の入力→保存→cat往復、履歴の再起動永続性）。

```sh
python3 tests/qemu_test.py          # 全チェック
python3 tests/qemu_test.py fs net   # 個別チェック
python3 tests/qemu_test.py gui      # GUIチェック（画面色・Term入力・ドラッグ・ESC復帰＋res設定・800×600・再起動永続性）
python3 tests/qemu_test.py tls      # TLSチェック（下記）
python3 tests/qemu_test.py apps     # アプリインストールチェック（下記）
python3 tests/qemu_test.py jstest   # JSエンジン自己テスト（JSRESULT照合）
python3 tests/qemu_test.py web      # グラフィカルブラウザチェック（下記）
python3 tests/qemu_test.py uefi     # UEFI/GOPブートチェック（OVMF必須、下記）
```

UEFIチェック（`uefi`）：同じ ISO を OVMF（`/usr/share/qemu/OVMF.fd`、qemu-system-x86_64）で起動し、シェル到達、起動ログの UEFI 告知、GUI が 1024×768 で立ち上がりデスクトップが描かれること、ESC 復帰後に `gfxstats` が動作することを確認します（GRUB がタグ8を渡さないため描画は VBE バックエンドです）。あわせて `res` チェックには 1280×1024 の起動・デスクトップ表示も含まれます。

ブラウザチェック（`web`）：テストサイトを :8080 で配信し、800×600 で検証します。`web` コマンドでブラウザ **ウィンドウ** が開いてページが描かれること（body bgcolor のピクセル数＋ウィンドウ内タブストリップ）、□ボタンでの **最大化**、リンククリック遷移、ツールバーの戻る／進むボタン、PgDnスクロール、Ctrl+T 新規タブ＋アドレスバー入力での遷移、タブ切替で他タブのページが保持されること、Ctrl+W でのタブ閉鎖、**ページ内JS**（例外を投げるスクリプトが後続を止めないこと、`getElementById(...).textContent` 代入で空要素に文字が描画されること、`document.write` の追記 — いずれも描画ピクセルで照合）、ウィンドウの [x] で閉じること、デスクトップアイコンのダブルクリックで再表示されること、ESCでのシェル復帰、そしてローカルTLSサーバ（:8446、テストCA証明書）からの **HTTPSページ描画** を確認します。v1.0 ではさらに：**CSS**（外部シート含む背景色・文字色・中央寄せ見出し・`display:none`・padding のピクセル照合）、**画像**（PNGの取得・デコード・拡縮配置）、**失敗遷移の堅牢性**（404／証明書エラー／DNS失敗／閉ポート／無応答ホスト／リダイレクト過多／ループの各ケースでブラウザが開いたまま従来ページが保持されること）、2ホップリダイレクトの着地、**巨大ページ**（300KB）の切り捨て読み込み、**フォーム**（エコーサーバ :8083 へ GET 送信した入力値が結果ページの背景色に反映されること、チェックボックスで送信値が変わること、POST＋Enter暗黙送信）、**Cookie**（初回なし→再読み込みで送信されること）を検証します。なおゲストの PS/2 マウスは速い／大きいデルタ移動でパケットを取りこぼすことがあるため、フォーム操作のクリックは小刻みな移動＋フォーカスリング確認＋リトライで行います。あわせて `jstest` グループが Duktape の評価結果 `JSRESULT shiro-js|7|610|9` を照合します。また `gui` グループには、800×600 でウィンドウを約3秒ドラッグして `gfxstats` の平均FPSを照合するチェック（`gfxstats:`）が含まれます。

TLSチェック（`tests/tls/`、フィクスチャ証明書はopensslで生成したテスト用）：ホストでTLSサーバを2つ立て、(1) テストCAの証明書（:8443）では `browse https://10.0.2.2:8443/` がページを取得でき TLS 1.2 が表示されること、(2) **無関係なCA** の証明書（:8444）は `certificate not trusted` で拒否されること、(3) 実サイト `browse https://example.com` が "Example Domain" を表示することを確認します。

アプリチェック（`apps`）：テストサイト（ビルド済み `calc` を配置）から `install http://10.0.2.2/calc` → `apps` 一覧 → `run calc` で `2+3*4` = 14 と `(2+3)*4` = 20 を検証 → 再起動後も登録と実行が生きていること → `uninstall` で消えること、までを通しで確認します。あわせてローカルTLSファイルサーバ（:8445、テストCA証明書）からの `install https://...`＋名前明示指定と、重複インストールの拒否も検証します。
注意：このサンドボックス環境ではQEMUからの外向きUDPが塞がれているため、テスト時は QEMU の guestfwd 経由で DNS-over-TCP ヘルパー（`tests/dnsfwd-tcp`、10.0.2.100:8053）を使います。通常の環境ではOS側の通常のUDP DNS（10.0.2.3）がそのまま動きます（OS側にもDNS-over-TCPフォールバックが入っています）。

## 制限
- HTTPSは TLS 1.2 まで（TLS 1.3非対応）。トラストアンカーは Mozilla バンドル中心の120ルート（v0.7.1、上記「HTTPS / TLS」参照）で大半の実サイトを検証できるが、バンドル外のルートで終わるチェーンは検証できない
- グラフィカルブラウザは HTML/CSS/JS の小さなサブセットのみ（CSS・画像・フォーム・Cookie は v1.0 でサブセット対応。JSアプリ系サイトは非対応。詳細は「グラフィカルブラウザ」）
- 起動は BIOS（GRUB Multiboot1/2）または UEFI（GRUB EFI＋Multiboot2）に対応。GRUB の EFI 版がフレームバッファタグを渡さないため GOP バックエンドは未使用で、UEFI時も描画は DISPI/VBE です（上記「UEFI ブートと GOP の現状」参照）。UEFI時はテキストモードのグリフが実画面に描画されません（テキストメモリ自体は正常）。Secure Boot には未対応
- 壁紙・サイドバー・ガラス風タイトルバーは VBE／GOP の 32bpp 時のみ（モード13hではグラデーション＋単色タイトルバー）。デスクトップのラベルは英字のみ（日本語フォント未搭載）
- ファイルは連続配置のみ、最大64ファイル、名前は27文字まで
- ユーザープログラムは単一プロセスのみ（fork等なし）。終了/例外でシェルに戻る
